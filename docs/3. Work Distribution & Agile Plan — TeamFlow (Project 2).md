| **FE** | Frontend Developer | React app, routing, state, forms, Kanban, dashboards, API integration on the client |

### Scrum roles

- **Product Owner (PO):** UX lead owns the backlog order and acceptance criteria, using Doc 1 as the source. PO has the final say on scope trade-offs.
- **Scrum Master (SM):** rotates weekly (Sprint 1: QA · Sprint 2: FE · Sprint 3: DB · Sprint 4: BE). SM runs ceremonies, removes blockers, keeps the board honest.
- **Development Team:** all five members, cross-functional. Everybody reviews PRs outside their own layer at least once per sprint.

### Backup owners (if someone is blocked or absent)

UX ↔ FE · BE ↔ DB · QA ↔ BE (tests) / FE (E2E). Backup must be briefed at each Wednesday sync.

## 2. Agile Working Model

### 2.1 Cadence (per sprint)

| When | Ceremony | Length | Output |
| --- | --- | --- | --- |
| Day 1 | Sprint Planning | 60 min | Sprint goal, committed stories, owners, estimates |
| Daily | Stand-up | 15 min | Yesterday / Today / Blockers (written in team chat if async) |
| Day 3 | Backlog refinement + integration check | 30 min | Next sprint stories ready; API/UI mismatches fixed |
| Day 5 | Sprint Review (demo) | 45 min | Working increment demonstrated from `main` |
| Day 5 | Retrospective | 30 min | 2–3 improvement actions logged |

### 2.2 Artifacts

- **Product backlog:** GitHub Projects board, columns: Backlog → Ready → In Progress → In Review → Testing → Done.
- **Sprint backlog:** stories labelled `sprint-1` … `sprint-4`, `module:Mx`, `role:UX/FE/BE/DB/QA`, `priority:M/S/C`.
- **Story format:** *As a \<role>, I want \<capability> so that \<benefit>.* with acceptance criteria in Given/When/Then.
- **Estimation:** story points (1, 2, 3, 5, 8). Anything above 8 must be split. Target capacity: about 20–25 points per person per sprint.
- **Tracking:** burndown (points remaining vs days) updated daily by SM; sprint velocity recorded for planning the next sprint.

### 2.3 Definition of Ready (story can enter a sprint)

- Linked to requirement ID(s) from Doc 1
- Acceptance criteria written and understood
- UI design (or wireframe) attached if the story has UI
- API contract exists in `openapi.yaml` if the story crosses FE/BE
- Dependencies identified and unblocked or scheduled
- Estimated and ≤ 8 points

### 2.4 Definition of Done (story is complete)

- Code merged to `main` through reviewed PR, CI green (lint + tests)
- Server-side validation and authorization implemented and tested
- Unit/API tests added; UI tested at 360 / 768 / 1280 px
- Empty, loading and error states handled
- Accessibility basics: labels, focus order, contrast
- OpenAPI/README/docs updated where behaviour changed
- Demonstrated in sprint review; accepted by PO

## 3. Collaboration Rules (so the five of us work as one)

### 3.1 Contract-first handoffs

1. **UX → FE:** wireframe + component spec (states, sizes, spacing, ARIA notes) before FE starts a screen. FE and UX do a 10-minute walkthrough.
2. **BE ↔ FE:** BE and FE agree the endpoint contract in `openapi.yaml` through a PR **before** coding. QA runs a mock server (Prism/MSW) so FE is never blocked by BE.
3. **BE ↔ DB:** DB owns migrations; BE requests schema changes via a story/PR to `database/migrations`. No schema change outside migrations.
4. **QA ↔ everyone:** every story gets a test owner. QA reviews acceptance criteria during refinement and writes tests in parallel with the feature.
5. **Daily integration:** every developer merges to `main` at least once a day; no branch lives longer than 2 days.

### 3.2 Git workflow

- Branches: `main` (always runnable, protected) ← `feature/<module>-<story-id>-short-name`, `fix/…`, `docs/…`, `test/…`.
- Commit style (Conventional Commits): `feat(tasks): add assignee validation`, `fix(auth): reject expired refresh token`, `test(authz): cross-org task access`, `docs(api): add comments endpoints`, `chore(ci): add playwright job`.
- **Pull requests:** small (< 400 lines when possible), linked to story, template with checklist (tests, docs, screenshots), **1 approval minimum** (2 for authz/auth/migrations), CI must pass, squash-merge.
- Migrations: one file per change, never edit a merged migration; add a new one.
- Secrets: never commit `.env`; only `.env.example`.

### 3.3 Communication

- One team chat channel + one for PR/CI notifications; blockers raised **immediately**, not at the next stand-up.
- Decisions recorded in `docs/decisions.md` (ADR-lite: date, decision, reason).
- Design handoff via shared Figma file; API via `openapi.yaml`; tasks via the board.

## 10. Risks and Contingency

| Risk | Trigger | Response |
| --- | --- | --- |
| Sprint overcommit | Burndown flat by Day 3 | PO drops Should/Could stories; pair on the blocker |
| FE blocked by BE | Endpoint not ready | Use Prism/MSW mock from contract; BE prioritizes contract PRs |
| Merge conflicts | Long-lived branches | Max 2-day branches; rebase daily; small PRs |
| Authz regression | New endpoint lacks tests | PR template requires “authz test added”; QA blocks merge |
| Environment drift | “Works on my machine” | Docker Compose DB, `.env.example`, setup verified by a different member each sprint |
| Late discovery of design gaps | Review in Week 4 | Mid-sprint integration check, usability test in Sprint 2 and 4 |
| Member unavailable | Missed 2 stand-ups | Backup owner takes critical stories; PO re-plans |
