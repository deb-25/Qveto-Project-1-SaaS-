# Modulation & System Design

**Project 2: Project Management & Team Collaboration SaaS** (*TeamFlow*) Companion to Document 1 (Requirements) · v1.0 · 17 Oct 2026

 *

## 1\. Architecture Overview

TeamFlow is a three-tier web application with a thin background-job layer.

```markdown
[ Browser: React + TS SPA ]
        |  HTTPS / JSON (REST, /api/v1)
        v
[ Express API ]
  routes -> middleware (auth, org scope, permission) -> controllers
        -> services (business rules) -> repositories (SQL, always org-scoped)
        |                      |                     |
        v                      v                     v
[ PostgreSQL ]        [ Private file storage ]   [ Job runner (node-cron) ]
                       storage/ (not in Git)      overdue scan, email retry
```

**Design principles**

1. Contract first: API is defined in OpenAPI before it is coded, so frontend and backend work in parallel.
2. Layering: controllers never touch SQL; repositories never contain business rules.
3. Tenant safety by construction: repositories require orgId as a parameter; there is no “find task by id” without org scope.
4. One transaction per business action: task move = update task + insert activity + insert notifications.
5. Fail clearly: consistent error format, empty states, and validation messages.

## 2\. Multi-Tenant & Authorization Design

### 2.1 Request pipeline

```rust
authenticate (JWT) -> resolveOrg (:orgId in path) -> loadMembership
   -> requireOrgRole([...]) -> requireProjectAccess (employees)
   -> validate (Zod) -> controller
```

| Step | What it does | Failure |
| --- | --- | --- |
| authenticate | Verifies access token, loads `req.user` | 401 |
| resolveOrg | Reads `orgId` from URL, confirms it exists | 404 |
| loadMembership | Finds user’s membership in that org | 403 if none |
| requireOrgRole | Checks role against the permission matrix (Doc 1 §8) | 403 |
| requireProjectAccess | Owner/Manager pass; Employee must be in `project_members` | 404 (hide existence) |
| validate | Zod schema on params, query, body | 422 |

### 2.2 Data-layer protection

*   All queries filter by `org_id`.
*   Child tables (tasks, comments, attachments) join through project to confirm `org_id` matches.
*   Central module `authz/` exports `can(user, action, resource)` used by services; UI only mirrors it for display.
*   A dedicated **cross-tenant test suite** loops over every endpoint using Org A tokens against Org B ids and expects 403/404.

## 3\. Module Catalogue

Eleven modules. Each lists purpose, UI, API, tables, rules and dependencies. Primary/supporting owners map to the 5 team roles: **UX** = UI/UX, **FE** = Frontend, **BE** = Backend, **DB** = DB & Storage, **QA** = Integration & Testing.

### M0 — Platform Foundation

*   **Purpose:** repository, tooling, environments, CI, shared conventions.
*   **Contents:** monorepo (`frontend/`, `backend/`, `database/`, `tests/`, `docs/`), Docker Compose (Postgres), ESLint/Prettier, env handling, error/response helpers, logger, health endpoint, CI pipeline.
*   **Owners:** QA (primary), all (support).
*   **Depends on:** nothing. **Blocks:** everything.

### M1 — Authentication & User Profile

*   **UI pages:** Login, Register, Profile, (Forgot password – optional).
*   **API:** `POST /auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `GET/PATCH /me`, `POST /me/password`.
*   **Tables:** `users`, `refresh_tokens`.
*   **Rules:** bcrypt/argon2 hashing, access token 15 min, refresh token 7 days (rotating, httpOnly cookie), login rate limit.
*   **Owners:** BE (primary), FE, DB, UX. **Depends on:** M0.

### M2 — Organization, Workspace, Team & Membership

*   **UI pages:** Org switcher, Create org, Members (invite/role change), Workspaces list, Team management, Org settings.
*   **API:** `POST /orgs`, `GET /orgs`, `/orgs/:orgId/members` (CRUD), `/orgs/:orgId/workspaces` (CRUD), `/workspaces/:id/teams` (CRUD), `/teams/:id/members`.
*   **Tables:** `organizations`, `memberships`, `workspaces`, `teams`, `team_members`.
*   **Rules:** last-Owner protection; removing a member removes project memberships; roles per Doc 1 §2.
*   **Owners:** BE (primary), FE, UX, DB. **Depends on:** M1.

### M3 — Projects & Project Members

*   **UI pages:** Projects list, Create/Edit project, Project Overview (progress, milestones, members).
*   **API:** `/orgs/:orgId/projects` (CRUD + archive/restore), `/projects/:id/members`, `/projects/:id/milestones`.
*   **Tables:** `projects`, `project_members`, `milestones`.
*   **Rules:** archived project is read-only; employees see only joined projects; project lead is a member.
*   **Owners:** BE (primary), FE, UX, DB. **Depends on:** M2.

### M4 — Tasks, Subtasks & Labels

*   **UI pages:** Task list (with filters), Create/Edit task modal, Task Details (shell), Label manager.
*   **API:** `/projects/:id/tasks` (list with filter/pagination, create), `/tasks/:id` (get, patch, archive), `/tasks/:id/subtasks`, `/tasks/:id/assign`, `/projects/:id/labels`, `/tasks/:id/labels`.
*   **Tables:** `tasks`, `labels`, `task_labels`.
*   **Rules:** status transition table; assignee must be project member; parent cannot be Done with open subtasks; `completed_at` automatic; optimistic locking via `version` (409).
*   **Owners:** BE (primary), FE, DB, UX, QA. **Depends on:** M3.

### M5 — Kanban Board

*   **UI pages:** Board with columns per status, card component, filters, Move-to menu, keyboard move.
*   **API:** `PATCH /tasks/:id/move` body `{status, position}`; `GET /projects/:id/board` (tasks grouped by status).
*   **Tables:** uses `tasks.status`, `tasks.position`.
*   **Rules:** position ordering uses gapped integers or fractional index; move is transactional; failed move rolls back in UI; ARIA live announcements.
*   **Owners:** FE (primary), UX, BE, QA. **Depends on:** M4.

### M6 — Collaboration: Comments, Attachments, Activity

*   **UI pages:** Task Details tabs: Comments, Attachments, Activity.
*   **API:** `/tasks/:id/comments` (CRUD), `/tasks/:id/attachments` (upload `multipart`, list, delete), `GET /attachments/:id/download`, `GET /tasks/:id/activity`, `GET /projects/:id/activity`.
*   **Tables:** `comments`, `attachments`, `activity_events`.
*   **Storage:** `storage/{orgId}/{projectId}/{uuid}.{ext}`; DB keeps original name, MIME, size, checksum, storage key, uploader.
*   **Rules:** allow-list types, 10 MB limit, MIME sniffing not only extension, random filenames, authorized streaming download with `Content-Disposition`, activity append-only.
*   **Owners:** BE and DB (co-primary), FE, UX, QA. **Depends on:** M4.

### M7 — Notifications & Overdue Engine

*   **UI pages:** Bell icon with unread badge, Notification center, (preferences – optional).
*   **API:** `GET /notifications`, `PATCH /notifications/:id/read`, `POST /notifications/read-all`, `GET /notifications/unread-count`.
*   **Tables:** `notifications` (type, recipient, task, payload, `dedupe_key`, `read_at`, `email_status`).
*   **Rules:** `dedupe_key` unique (e.g. `overdue:{taskId}:{dueDate}`); no self-notification; comment burst collapsing; overdue cron every 15 min (idempotent); email in simulated mode unless SMTP set.
*   **Owners:** BE (primary), FE, DB, QA. **Depends on:** M4, M6.

### M8 — Reports & Analytics

*   **UI pages:** Project dashboard, Reports (completion, on-time, workload, trend), CSV export.
*   **API:** `GET /projects/:id/stats`, `GET /orgs/:orgId/reports/completion|ontime|workload|trend` with `from`, `to`, `projectId` filters.
*   **Tables:** none new; SQL aggregates (optional `task_daily_snapshot` for trend).
*   **Rules:** formulas exactly as Doc 1 §9; zero denominators return `null`; employees limited to own projects.
*   **Owners:** BE and DB (co-primary), FE, UX, QA. **Depends on:** M4, M6.

### M9 — My Work Dashboard

*   **UI page:** assigned tasks grouped by Overdue / Today / This week / Later.
*   **API:** `GET /me/work` (cross-project within the current org).
*   **Owners:** FE (primary), BE, UX. **Depends on:** M4, M7.

### M10 — Quality, Security & Deployment (cross-cutting)

*   **Contents:** unit/API/E2E tests, cross-tenant suite, security review checklist, performance indexes, error logging, deployment config, README and final report.
*   **Owners:** QA (primary), all (support). **Runs through every sprint.**

## 5\. API Conventions

*   **Base path:** `/api/v1`. Resource nesting under `/orgs/:orgId/...` for tenant scope.
*   **Auth:** `Authorization: Bearer <access_token>`; refresh cookie is httpOnly + SameSite.
*   **Success:** `{ "data": ..., "meta": { "page": 1, "pageSize": 20, "total": 134 } }`
*   **Error:** `{ "error": { "code": "VALIDATION_ERROR", "message": "...", "details": [{"field":"title","issue":"required"}], "requestId": "..." } }`
*   **Status codes:** 200, 201, 204, 400, 401, 403, 404, 409 (version conflict), 413 (file too big), 415 (type not allowed), 422 (validation), 429, 500.
*   **Pagination:** `?page=&pageSize=` (default 20, max 100); **sorting:** `?sort=-dueDate`.
*   **Dates:** ISO-8601 UTC strings.
*   **IDs:** UUID v4.
*   **Docs:** `docs/api/openapi.yaml`, served with Swagger UI at `/api/docs` in dev.

| comments | id, org\_id, task\_id, author\_id, body, edited\_at, created\_at |  |
| attachments | id, org\_id, task\_id, uploader\_id, original\_name, mime\_type, size\_bytes, checksum, storage\_key, created\_at, deleted\_at |  |

**Enums:** `org_role`, `project_status`, `task_status`, `task_priority`, `notification_type`, `activity_type`, `email_status` (`none`, `simulated`, `sent`, `failed`).

**Integrity:** composite foreign keys such as `(task_id, org_id)` → `tasks(id, org_id)` so a comment can never point to a task in another org; CHECK constraints for status/priority; subtask depth limited by service rule plus constraint that a parent has no parent.

## 8\. Key Sequence Flows

### 8.1 Move a task on the board

1. FE optimistic update, calls PATCH /tasks/:id/move.
2. API authenticates, resolves org, checks project access.
3. Service validates transition and version.
4. Transaction: update task (status, position, completed_at) → insert activity event → insert notifications (if needed).
5. Returns updated task; FE confirms, or rolls back on error and shows message.

### 8.2 Assign a task

1. Validate assignee belongs to project.
2. Update assignee_id; insert task.assigned activity.
3. Create notification for assignee unless assignee is the actor (dedupe key assigned:{taskId}:{assigneeId}:{version}).

### 8.3 Upload and download an attachment

1. Upload: auth → project access → multer size limit → type allow-list + MIME sniff → write to storage/ with random name → insert metadata → activity event.
2. Download: auth → project access → load metadata scoped by org → stream file; never expose a storage path.

### 8.4 Overdue scan (cron, every 15 min)

1. Select open eligible tasks with due_date < now() and an assignee.
2. Insert notifications with dedupe_key = overdue:{taskId}:{dueDate} using ON CONFLICT DO NOTHING.
3. Log counts; safe to re-run.
