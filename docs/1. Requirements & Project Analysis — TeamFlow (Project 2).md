**Project 2: Project Management & Team Collaboration SaaS** (working name: *TeamFlow*) Team of 5 · 4-week Agile plan · Document v1.0 · 17 Oct 2026

 *

## 1\. Introduction

### 1.1 Purpose

This document defines **what** we are building and **how** it will behave, based on the Project 2 problem statement. It is the single source of truth for scope, requirements, rules and acceptance criteria. Every user story in our backlog must trace back to a requirement ID in this document.

### 1.2 Problem statement (from the PS)

Teams need a shared view of ownership, priorities, deadlines, dependencies and work status. When project information is scattered across messages and spreadsheets, overdue tasks and blockers are hard to spot and managers lack reliable progress reporting. We must build a **multi-organization** collaboration platform that keeps project and task activity in one place and guarantees users can only access resources permitted by their **organization and role**.

### 1.3 Product vision

A secure, multi-tenant web app where an organization can create workspaces, teams and projects; plan and assign tasks on a Kanban board; collaborate through comments and attachments; get notified about what matters; and see trustworthy progress reports.

### 1.4 In scope

*   Organizations, memberships, workspaces, teams, projects, project members
*   Tasks, subtasks, labels, priorities, due dates, assignees, status workflow
*   Kanban board with drag-and-drop **and** keyboard/accessible alternative
*   Comments, file attachments, activity history
*   In-app notifications (+ optional email), overdue detection
*   Dashboards and reports with documented calculation rules
*   Role-based access (Owner, Manager, Employee) enforced at API and data layer
*   Tests, deployment, documentation, final presentation

### 1.5 Out of scope (documented limitations)

*   Real payments/billing, SSO/OAuth providers, mobile native apps
*   True real-time sync (we use **polling**, documented as a limitation; WebSocket/SSE is a stretch goal)
*   Task dependencies graph/Gantt (only simple “blocked” label; stretch goal)
*   Real production email delivery (email runs in a clearly labelled simulated/dev mode unless SMTP is configured)

### 1.6 Glossary

| Term | Meaning |
| --- | --- |
| Organization (org) | The tenant. All data belongs to exactly one org. |
| Workspace | A container inside an org (e.g. “Engineering”, “Marketing”). |
| Team | A group of org members inside a workspace. |
| Project | A body of work inside a workspace, with its own members and tasks. |
| Task / Subtask | Unit of work; a subtask has a parent task (one level deep). |
| Eligible task | A task counted in KPIs: not archived and not cancelled (see §9). |

## 2\. Users and Roles

| Role | Level | Who they are | Summary of power |
| --- | --- | --- | --- |
| **Owner** | Organization | Creator/admin of the org | Everything in the org, including members, roles, deletion of org data |
| **Manager** | Organization | Team/project lead | Create and manage workspaces/teams/projects, assign work, see all org projects and reports |
| **Employee** | Organization | Regular contributor | Sees only projects they are a member of; works on tasks, comments, attaches files |

**Rules**

1. A user can belong to multiple organizations with a different role in each.
2. The org role is the ceiling; project membership grants access for Employees.
3. Owners and Managers can view all projects in their org. Employees only see projects where they are a project member.
4. Every request is evaluated as: authenticated → member of this org → role allows action → resource belongs to this org (and project, if employee).
5. An org must always keep at least one Owner.

## 4\. Functional Requirements

Priority uses MoSCoW: **M** = Must, **S** = Should, **C** = Could.

### 4.1 Authentication & Users (AUTH)

*   **FR-AUTH-01 (M)** Register with name, email, password; email unique; password policy enforced (min 8 chars, mixed).
*   **FR-AUTH-02 (M)** Login/logout with secure session or tokens that expire; passwords hashed (bcrypt/argon2).
*   **FR-AUTH-03 (M)** Token refresh/session renewal; invalid or expired tokens return 401.
*   **FR-AUTH-04 (M)** View/update own profile (name, avatar optional, timezone display preference).
*   **FR-AUTH-05 (S)** Change password; rate-limit login attempts.
*   **FR-AUTH-06 ©** Password reset via email link (simulated mail allowed).

### 4.2 Organization, Workspace, Team, Membership (ORG)

*   **FR-ORG-01 (M)** A new user can create an organization and becomes its Owner.
*   **FR-ORG-02 (M)** User can switch between orgs they belong to; every API call is org-scoped.
*   **FR-ORG-03 (M)** Owner/Manager can invite or add members by email and assign an org role; Owner can change roles or remove members.
*   **FR-ORG-04 (M)** Create, rename, archive workspaces (Owner/Manager).
*   **FR-ORG-05 (M)** Create teams inside a workspace; add/remove members (Owner/Manager).
*   **FR-ORG-06 (M)** Prevent removing the last Owner; removed members lose access immediately.
*   **FR-ORG-07 (S)** Organization settings page (name, default timezone).

### 4.3 Projects (PRJ)

*   **FR-PRJ-01 (M)** Create project in a workspace with name, description, key, start/target dates, status (Planned, Active, On Hold, Completed, Archived).
*   **FR-PRJ-02 (M)** Add/remove project members and set project lead (Owner/Manager).
*   **FR-PRJ-03 (M)** Project overview page: progress %, status distribution, members, milestones.
*   **FR-PRJ-04 (S)** Milestones (name, due date) shown on overview.
*   **FR-PRJ-05 (M)** Archive/restore project; archived projects are read-only.

### 4.4 Tasks, Subtasks, Labels (TSK)

*   **FR-TSK-01 (M)** Create/read/update/delete (soft-delete or archive) tasks with title, description, status, priority, due date, assignee, labels.
*   **FR-TSK-02 (M)** Priorities: Low, Medium, High, Urgent. Statuses: Backlog, To Do, In Progress, In Review, Done, Cancelled.
*   **FR-TSK-03 (M)** Assign/unassign a task to a **project member** only.
*   **FR-TSK-04 (M)** Subtasks (one level) with own status and assignee; parent shows subtask progress.
*   **FR-TSK-05 (M)** Labels per org/project; apply multiple labels to a task.
*   **FR-TSK-06 (M)** Status transitions validated server-side (see §10); completion timestamp set when entering Done, cleared if reopened.
*   **FR-TSK-07 (M)** Filter/search tasks by status, assignee, priority, label, due date range, text; paginated.
*   **FR-TSK-08 (S)** Concurrent edit protection (version field / `updated_at` check; return 409 on conflict).

### 4.5 Kanban Board (KAN)

*   **FR-KAN-01 (M)** Board per project with a column per status; task cards show title, priority, assignee, due date, labels, overdue badge.
*   **FR-KAN-02 (M)** Drag-and-drop between columns and reorder within a column; position persists.
*   **FR-KAN-03 (M)Accessible alternative:** each card has a “Move to…” menu and keyboard-operable move (arrow keys + Enter) with screen-reader announcements.
*   **FR-KAN-04 (M)** Optimistic UI with rollback and error message if server rejects the move.
*   **FR-KAN-05 (S)** Board filters (assignee, label, priority) and WIP indicator per column.

### 4.6 Collaboration (COL)

*   **FR-COL-01 (M)** Comments on tasks (add, edit own, delete own; Manager/Owner can delete any); @mention optional.
*   **FR-COL-02 (M)** File attachments on tasks with type allow-list and size limit (e.g. png, jpg, pdf, docx, xlsx, txt, zip; max 10 MB) validated on server.
*   **FR-COL-03 (M)** Attachments stored in private storage; downloads go through an authorized API endpoint (no public URLs).
*   **FR-COL-04 (M)** Activity events recorded for: task created/updated/moved/assigned/due-date changed, comment added, attachment added/removed, member changes. Each has actor, timestamp, before/after summary.
*   **FR-COL-05 (M)** Task details page shows subtasks, comments, attachments, and activity history.

### 4.7 Notifications & Deadlines (NTF)

*   **FR-NTF-01 (M)** In-app notifications for: assigned to task, comment on a task I own/assigned/follow, due date changed, task overdue.
*   **FR-NTF-02 (M)** Notification center: list, unread count badge, mark read, mark all read.
*   **FR-NTF-03 (M)** Overdue detection by scheduled job using the documented timezone rule (§9); one overdue notification per task per due date (dedupe).
*   **FR-NTF-04 (M)** Avoid noise: no notification to the actor about their own action; collapse repeated comments within a short window.
*   **FR-NTF-05 (S)** Optional email notifications via SMTP; delivery status recorded; clearly labelled **simulated** if no SMTP.
*   **FR-NTF-06 ©** Per-user notification preferences.

### 4.8 Dashboards & Reports (RPT)

*   **FR-RPT-01 (M)My Work** page: assigned tasks, upcoming deadlines (next 7 days), overdue items.
*   **FR-RPT-02 (M)** Project dashboard: progress %, status distribution, overdue count, assignment coverage.
*   **FR-RPT-03 (M)** Reports page: task completion rate, on-time completion rate, workload per member, progress trend over time; filters by project and date range.
*   **FR-RPT-04 (M)** Empty-state handling and a visible “how this is calculated” note for each metric.
*   **FR-RPT-05 (S)** Export report as CSV.

## 5\. Non-Functional Requirements

| Area | Requirement |
| --- | --- |
| **Security** | Server-side validation on every input; parameterized queries; helmet headers; CORS allow-list; rate limiting on auth; secrets only in env vars; no stack traces to clients; private file storage; tenant isolation at data layer. |
| **Authorization** | Permission checks in reusable backend functions/middleware, never UI-only. Cross-org access returns 404/403 and is covered by tests. |
| **Performance** | Typical list APIs under 500 ms on seed data; pagination everywhere (default 20, max 100); indexes on `org_id`, `project_id`, `assignee_id`, `status`, `due_date`. |
| **Usability & Accessibility** | Responsive (mobile 360px, tablet, desktop); WCAG 2.1 AA targets: contrast, focus states, labels, keyboard Kanban alternative, ARIA live region for moves. |
| **Reliability** | DB transactions for multi-row writes (task move + activity + notification); idempotent overdue job; clear error + empty states. |
| **Maintainability** | TypeScript, ESLint/Prettier, layered code (routes → services → repositories), migrations for all schema changes, API documented with OpenAPI. |
| **Observability** | Structured error logging with request IDs; health endpoint `/api/v1/health`. |
| **Reproducibility** | One-command local setup (Docker Compose for DB), `.env.example`, seed script, documented test commands. |
| **Time handling** | All timestamps stored in UTC; displayed in the user/org timezone. |

## 7\. Data Requirements

### 7.1 Core entities

`users`, `organizations`, `memberships`, `workspaces`, `teams`, `team_members`, `projects`, `project_members`, `milestones`, `tasks`, `labels`, `task_labels`, `comments`, `attachments`, `activity_events`, `notifications`, `refresh_tokens`, plus lookup/enum definitions for task status and priority.

### 7.2 Data rules

1. Tenant integrity: every org-owned table carries org_id (directly or via a verifiable parent). Child rows must have the same org_id as their parent (enforced with composite foreign keys or service checks + tests).
2. Tasks hold assignee_id, due_date (timestamptz), completed_at, parent_task_id (null for top-level), position (for ordering), archived_at, version.
3. Assignee must be a member of the task’s project.
4. Soft delete/archive instead of hard delete for tasks, projects and workspaces to keep history intact.
5. Activity events are append-only.
6. Seed data: at least two organizations with users in each role, workspaces, teams, projects, tasks in every status, overdue tasks, comments, sample attachments (all synthetic).

## 9\. Business Rules and KPI Definitions

**Timezone rule:** timestamps stored in UTC. “Now” for overdue checks is server UTC time. A task is overdue when `due_date < now` and status is not Done/Cancelled. Date-only comparisons use the org’s default timezone.

**Eligible task:** `archived_at IS NULL` AND `status != Cancelled`. Archived and cancelled tasks are excluded from all rates and counts, except where stated.

| KPI | Formula (documented in the UI) |
| --- | --- |
| Task completion rate | Done eligible tasks ÷ all eligible tasks in the selected project and time window (window uses `created_at`/`completed_at`, shown to user) |
| On-time completion rate | Tasks with `completed_at <= due_date` ÷ completed tasks that have a due date |
| Overdue task count | Open eligible tasks with `due_date < now` |
| Project progress | Done non-archived, non-cancelled tasks ÷ all non-archived, non-cancelled tasks (top-level tasks only; subtasks roll up into parent display) |
| Assignment coverage | Active tasks with an assignee ÷ all active tasks (active = eligible and not Done) |
| Notification processing | Notifications created, delivered (visible in list), read; in-app state is reported separately from email delivery |
| Authorization integrity | Automated tests prove cross-org and cross-role access is blocked |
| Workload indicator | Open eligible tasks per assignee (optionally weighted by priority) |

If a denominator is zero the UI shows “No data” instead of 0% or NaN.

## 10\. Task Status Workflow

Backlog → To Do → In Progress → In Review → Done

*   Forward and backward moves between adjacent active statuses are allowed.
*   Backlog may move directly to To Do or In Progress.
*   Any status may move to **Cancelled**; Cancelled may be reopened to Backlog/To Do (Manager/Owner only).
*   Done may be reopened to In Progress or In Review; this clears `completed_at`.
*   A parent task cannot be set to Done while it has open subtasks (returns validation error).
*   Archived tasks cannot change status until restored.
*   Every transition writes an activity event and, if relevant, a notification, **in one DB transaction**.

## 12\. Acceptance Criteria

*   **AC-01 Authorization:** an Employee of Org A gets 403/404 on any read or write of Org B’s projects, tasks, comments and attachments; an Employee cannot access a project they are not a member of; role-restricted actions in §8 are denied.
*   **AC-02 Tasks:** a Manager can create a project, add members, create tasks with subtasks, assign, set due dates and move a task through the full workflow; invalid transitions are rejected with a clear error.
*   **AC-03 Kanban:** a task can be moved by mouse drag, by keyboard, and via the “Move to…” menu; a failed move rolls back.
*   **AC-04 Collaboration:** comments, attachments and activity entries appear on the task; an unauthorized user cannot download an attachment; disallowed type/oversize files are rejected server-side.
*   **AC-05 Notifications:** assignment, comment, due-date change and overdue each create exactly one notification for the right users; actor is not notified of own action.
*   **AC-06 Reports:** every metric equals a manual calculation on seed data; empty datasets render properly.
*   **AC-07 Quality:** responsive at 360px, 768px, 1280px; CI runs lint and tests; README setup works from a clean clone.
*   **AC-08 Demo:** two organizations demonstrated live, proving one org cannot see the other’s data.
